# Сравнение DWH на PostgreSQL и Data Lakehouse для FinUnion + RetailBank  

## DWH на PostgreSQL

| Параметр | Описание |
|----------|----------|
| **Хранение** | Табличные схемы, колонковый тип, индексы. |
| **Стоимость** | Высокая стоимость SSD‑хранилища при растущих объёмах (т.е. 10‑20 млн записей/день → ~5 TB за год). |
| **Производительность** | Отлично подходит для агрегированных запросов, сложных JOIN‑ов, отчётных витрин. |
| **Поддержка** | Широкий набор инструментов (dbt, Airflow, pgAdmin). |
| **Ограничения** | Неэффективен для “cold” данных (> 2 года), ограничена поддержка schema‑evolution, тяжелый процесс загрузки больших файлов. |

## Data Lakehouse (Iceberg + Trino)

| Параметр | Описание |
|----------|----------|
| **Хранение** | Файлы Parquet в объектном хранилище (S3‑compatible). Iceberg управляет метаданными, поддерживает snapshot, time‑travel. |
| **Стоимость** | Дешёвое “cold” хранилище, стоимость растёт линейно, но в разы ниже SSD. |
| **Производительность** | Trino умеет эффективно сканировать партиционированные файлы; для интенсивных аналитических запросов почти сравнимо с DWH. |
| **Гибкость** | Schema‑evolution без миграций, поддержка полуструктурированных данных (JSON, Avro). |
| **Поддержка** | Интеграция с dbt (Iceberg‑adapter), Airflow, DataHub. |
| **Ограничения** | Высокая латентность при мелких запросах, требует настройки кеша (e.g., Hive Metastore) и оптимального партиционирования. |

## Выбранный подход

| Период | Выбор | Обоснование |
|--------|------|------------|
| **Промежуточное (3 мес.)** | **Hybrid:** DWH (PostgreSQL) + Kafka → Lake (raw) | Быстрая реализация: existing DWHs реплицируются, а события начинают поступать в Kafka → S3 (raw). |
| **Финальное (12 мес.)** | **Full Lakehouse + DWH** | Основные исторические и событийные данные полностью мигрируют в Iceberg‑Lake; регламентированная отчётность остаётся в PostgreSQL для гарантированной ACID‑согласованности. |

## Роль Apache Iceberg и Trino

* **Iceberg** – обеспечивает **табличный слой** над объектным хранилищем, управляет схемой, версиями, partition‑pruning, и **time‑travel** (полезно для регуляторных аудитов). |
* **Trino** – единый **SQL‑движок** с возможностью **federated queries**:  
  * Запросы к Lakehouse (Iceberg) и к PostgreSQL‑DWH в одном `SELECT`.  
  * Поддержка пользовательских функций, security‑plugins, и интеграции с DataHub.  

## Распределение данных

| Категория данных | Где хранится | Почему |
|------------------|--------------|--------|
| **Критические финансовые отчёты** (балансы, регуляторные формы) | **PostgreSQL DWH** | Требуется строгая согласованность, быстрый отклик, поддержка транзакций. |
| **События карт, транзакций, лог‑данные** | **Data Lakehouse (Iceberg)** | Объём в терабайтах, требуется историзация, гибкая схема, доступ для Data‑Science. |
| **Справочники (продукты, тарифы, контрагенты)** | **MDM (Customer & Product Hub)** + **Iceberg** (для versioned catalog) | MDM – золотая запись; Iceberg – версия и быстрое чтение. |
| **Документы (сканы договоров, паспорта)** | **Object Store (S3)** | Неструктурированные файлы, дешёвое хранение, ссылки в MDM. |
| **BI‑витрины** | **PostgreSQL DWH** (агрегаты) + **Lakehouse** (raw) | BI‑инструменты используют DWH‑вью, а исследователи могут писать ad‑hoc запросы к Lakehouse через Trino. |

## Ограничения выбранного подхода

| Ограничение | Как mitigировать |
|-------------|-------------------|
| **Сложность оркестрации** (две платформы) | Airflow с разделёнными DAG‑ов, единой metadata‑db, CI/CD для dbt‑моделей. |
| **Двойное хранение** (в DWH и Lakehouse) | Чётко определить **доменные границы**: только агрегации в DWH, raw‑events только в Lakehouse. |
| **Обеспечение согласованности** (CDC → Lake → DWH) | Использовать **exactly‑once** semantics в Kafka (transactional producer), а также **outbox‑pattern** в core‑системах. |
| **Governance** (многообразие схем) | DataHub хранит schema‑registry, а также политики доступа (Ranger). |
| **Обучение персонала** | План обучения (Data Engineering, BI, Risk) включён в Roadmap (Task 4). |
