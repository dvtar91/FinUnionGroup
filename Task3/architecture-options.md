# Сравнение архитектурных вариантов

## Вариант 1 – DWH на PostgreSQL

| Плюсы | Минусы | Когда подходит | Применимость к FinUnion + RetailBank |
|-------|--------|----------------|--------------------------------------|
| **Простота** – одна СУБД, знакомый стек, быстрый запуск | **Ограничения масштабируемости** при больших объёмах исторических данных | Малый‑средний объём данных, быстрый старт, ограниченный бюджет | Подойдёт для **промежуточного** состояния (3 мес.) – можно быстро собрать базовые отчёты. |
| **Транзакционная согласованность** – ACID, удобные аналитические запросы | **Высокие затраты на хранение** при растущем lake‑массиве | Когда требуется регламентированная отчётность и консистентные расчёты | Не покрывает требования к обработке **многопетабайтных** исторических событий. |
| **Поддержка dbt** → модель трансформаций | **Отсутствие нативного поддержки schema‑evolution** | | |

## Вариант 2 – Data Lakehouse (Iceberg + Trino)

| Плюсы | Минусы | Когда подходит | Применимость к FinUnion + RetailBank |
|-------|--------|----------------|--------------------------------------|
| **Гибкость хранения** – файлы в объектном хранилище, поддержка всех форматов (Parquet, ORC) | **Сложность управления** (конфигурация Iceberg, Trino, метаданные) | Большие объёмы исторических, полуструктурированных данных, требуются как batch, так и ad‑hoc запросы | Идеально для **финального** состояния (12 мес.) – позволяет хранить все события карт, кредитов, логов и быстро их анализировать. |
| **Низкая стоимость** – объектное хранилище дешевле СУБД | **Latency** для тяжёлых аналитических запросов выше, чем в DWH | Когда важен **data‑science** и машинное обучение | Поддерживает **требования к Data Lake** (неструктурированные файлы, архивы). |
| **Schema‑evolution** без миграций, **time‑travel** (версии) | **Требуется отдельный SQL‑движок** (Trino) | | |
| **Unified access** – одинаковый SQL к lake и DWH через Trino | | | |

## Вариант 3 – Data Mesh

| Плюсы | Минусы | Когда подходит | Применимость к FinUnion + RetailBank |
|-------|--------|----------------|--------------------------------------|
| **Децентрализованное владение** – команды отвечают за свои data‑продукты | **Сложность организации** – требует сильного governance, стандартизации | Организации с большим числом автономных доменов, готовые инвестировать в self‑serve data platform | Часть **доменных** продуктов (Customer 360, Credit‑Analytics) можно оформить как mesh‑продукты, но полное mesh без сильного governance рискованно. |
| **Быстрое внедрение** новых доменов | **Дублирование инфраструктуры** (каждый домен поддерживает свои pipelines) | Когда критично время вывода новых аналитических функций | Подходит как **гибрид**: отдельные домены (Risk, Marketing) предоставляют data‑продукты, а ядро остаётся в Lakehouse/DWH. |
| **Self‑service** аналитика | **Согласованность данных** может пострадать без строгих контрактов | | |

### Выбор подхода

**Гибридный Lakehouse + DWH** с элементами Data Mesh для доменных data‑продуктов:

* **Lakehouse** – основной «запас» сырых и исторических данных (события карт, транзакций, логи).  
* **DWH (PostgreSQL)** – регламентированная, согласованная отчетность (финансовый, налоговый).  
* **Data Mesh** – 3–5 доменных data‑продуктов (Customer 360, Credit‑Risk, Product‑Catalog, AML‑Events) построены на Lakehouse, но публикуются через DataHub как самостоятельные сервисы.  

Такой подход покрывает потребности **операционных** и **аналитических** нагрузок, обеспечивает масштабируемость, гибкость и упрощает治理 (governance) через единый каталог.
