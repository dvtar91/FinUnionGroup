# Инкрементальный план миграции (6 этапов)

| Этап | Содержание | Ключевые результаты | Ожидаемая продолжительность |
|------|------------|---------------------|------------------------------|
| **Data Discovery & Governance** | • Инвентаризация всех таблиц, схем и потоков (FinUnion + RetailBank).<br>• Формирование **Data Catalog** в DataHub.<br>• Определение владельцев (Data Owner / Steward) для каждой сущности.<br>• Выявление критичных PII‑полей и классификация данных. | 📋 Полный реестр данных, первый набор метаданных в DataHub, матрица ответственности. | 3 недели |
| **MDM‑Bootstrap & Client ID Unification** | • Создание **MDM Customer Hub**.<br>• Настройка правил дедупликации (ИНН + паспорт + email).<br>• Автономный CDC‑коннектор из **FU CRM** и **RB CRM** → Kafka → MDM.<br>• Пилотный импорт 5 % клиентской базы, проверка совпадений.<br>• Выдача единого `customer_id`. | Унифицированный клиентский идентификатор, готовность к использованию в Core и BI. | 4 недели |
| **Integration‑Layer Consolidation** | • Внедрение **ESB** (MuleSoft/Wso2) как единого шлюза.<br>• Переписывание Point‑to‑Point интеграций в **REST‑API** + **Kafka**‑топики.<br>• Тестовый запуск **CDC** из Core FinUnion → Kafka → DWH (sandbox). | 🔗 Сокращённое количество точечных соединений, все потоки идут через единую шину. | 5 недели |
| **Core & Data Lakehouse Migration (Phased)** | **4.1** – Перенос исторических транзакций и карточных событий в **Lakehouse** (Iceberg). <br>**4.2** – Пилотный запуск **Hybrid OLTP/OLAP**: новые счета открываются в Target Core, а записи сразу реплицируются в Lakehouse (CDC).<br>**4.3** – Тестовая миграция 10 % кредитного портфеля в Target Core + DWH. | 📈 Доказательство концепции «Hybrid», 99,9 % репликация данных, слежение за latency < 2 сек. | 6 недели |
| **Cut‑over of Reporting & BI** | • Перенос всех регуляторных и управленческих отчётов из **RB DWH** в **Target DWH** (dbt‑модели).<br>• Обновление Looker‑моделей, переход на единые бизнес‑метрики.<br>• Параллельный запуск отчётов (двойной) 2 недели → сравнение контрольных сумм. | Совместимые отчёты, готовность к отключению legacy‑BI. | 4 недели |
| **Legacy De‑commission & Go‑Live** | • Финальная выгрузка остатков данных из **RetailBank CRM** и **RetailBank Core** → **Lakehouse**.<br>• **Точка невозврата**: как только DNS‑запись и баланс‑лоды переключаются на **MDM Customer Hub** и **Target Core**, старые CRM‑инстансы **выключаются** и больше не принимают записи.<br>• При откате **все новые изменения**, сделанные в MDM после точки невозврата, **бэкапятся** в отдельный **Change‑Log‑Bucket** (S3‑префикс `crm-rollback/`) и могут быть реплей‑им в старую CRM через специализированный импорт‑скрипт.<br>• Отключение **RetailBank CRM** и **RetailBank Core** после подтверждения согласованности данных.<br>• Обновление маршрутизации (DNS/Load‑Balancer) → Target Core.<br>• Пост‑мониторинг 30 дней, план «fast‑track» отката. | Полное функционирование целевой архитектуры без простоев; точка невозврата задокументирована и автоматизирована. | 3 недели |




### Ключевые контрольные точки

| Мильстоун | Критерий выхода |
|-----------|----------------|
| **M1** – Data Catalog готов | > 95 % сущностей задокументировано в DataHub |
| **M2** – Unified Customer ID | Дубли < 0,1 % в пилотных 5 % |
| **M3** – ESB в продакшн | 100 % Point‑to‑Point переключено |
| **M4** – Lakehouse ingest OK | CDC latency < 2 сек, data‑loss = 0 |
| **M5** – Reporting parity | Все KPI совпадают в двух системах ± 0,5 % |
| **M6** – Go‑Live | Отключены все legacy‑сервисы, KPI‑dashboards живут в единой системе |
