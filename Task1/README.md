# Задание 1. Анализ данных, сущностей и хранилищ

**Цель задания:** проанализировать данные двух организаций, выделить ключевые бизнес-сущности, описать связи между ними, классифицировать данные по критичности и предложить типы хранилищ.

## Конкретные задачи
**1. Выделите ключевые бизнес-сущности**

Определите не менее десяти ключевых сущностей данных, которые участвуют в объединении FinUnion и RetailBank.

Можно использовать стартовый список из описания кейса, но итоговый набор сущностей должен быть вашим архитектурным решением. Если вы добавляете или исключаете сущность, кратко объясните причину.

Для каждой сущности укажите:

* Название (например, Клиент)
* Описание — что отражает сущность
* Основные атрибуты (например, ФИО, ИНН, паспорт, телефон)
* Сущности, с которыми связана эта сущность
* Системы-источники, в которых сущность используется
* Критерий, по которому сущность попала в модель
* Проблемы качества — дубли, пропуски, разные форматы, устаревшие данные

**2. Постройте логическую модель данных**

Создайте ERD или логическую схему связей между ключевыми сущностями. Можно использовать PlantUML, Mermaid, Draw.io или Structurizr.

Минимально отразите связи между клиентами, счетами, договорами, продуктами, операциями и обращениями.

**3. Классифицируйте данные**

Создайте таблицу классификации данных, например, такую:

|Сущность|Категория данных|Критичность|Влияние на ИБ|Средства защиты|
|--------|----------------|-----------|-------------|---------------|
|Клиент|ПДн|Высокая|Утечка нарушает требования ИБ и законодательства|Шифрование, маскирование, RBAC, аудит|

**4. Предложите типы хранилищ**

Для разных групп данных предложите подходящий тип хранилища.

Нужно рассмотреть следующие типы:

* OLTP БД — для операционных данных: счетов, договоров, платежей
* MDM — для золотых записей клиентов и справочников
* DWH — для регламентированной отчётности и BI
* Data Lakehouse — для больших исторических и событийных данных
* Объектное хранилище — для документов, выгрузок, архивов
* Графовая БД — для связей клиентов и контрагентов, если они обоснованы
*Поисковый движок — для поиска по обращениям и клиентским данным, если он обоснован

**5. Используйте референсную модель BIAN**

Сопоставьте 8–10 ключевых сущностей с сервисными или близкими областями BIAN.

Не просто перечислите названия доменов, а объясните, как референсная модель помогает:

* унифицировать терминологию после слияния;
* определить границы владения данными;
* найти пересечения между системами FinUnion и RetailBank;
* подготовить целевые домены данных и data products.

Пример:

|Сущность|Возможная область BIAN|Зачем это нужно|
|--------|----------------------|---------------|
|Клиент|Party Data Management|Единый подход к клиентским данным|
|Счёт|Current Account|Унификация модели счёта|

Остальные сущности сопоставьте самостоятельно.
